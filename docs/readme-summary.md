## 0. 一句话概括

一个"大众点评"的简化实现。**单体后端 + 一系列"用共享内存数据结构替代数据库"的优化**：

- 会话、热点数据、库存、点赞、关注、位置、签到、UV —— 全部塞进 Redis（一个跨进程共享的数据结构服务器）
- MySQL 只做最终持久化
- 下单这类耗时路径改成"Redis 里原子预检 + 消息队列异步落库"
- nginx 托管前端页面并把 `/api` 转发给后端

README 的价值不在"怎么用"，而在**"每个业务问题用了什么数据结构/并发机制解决，为什么不用别的"**。

## 1. 技术栈：名词 → 你熟悉的 CS 概念

| 名词 | 它是什么 | 对应你熟悉的东西 |
|---|---|---|
| **Spring Boot** | Java Web 框架 | 一个运行时的"依赖装配器"（控制反转/依赖注入）：对象由容器创建并接线，你只写业务逻辑。内嵌 Tomcat 提供 HTTP 服务 |
| **MyBatis-Plus** | ORM（对象关系映射） | 关系表的行 ↔ 语言对象 的映射层，用方法链拼 SQL；附带分页插件（自动改写 `limit`） |
| **Redis** | 内存数据库 | **一个跑在网络另一端的、支持多种数据结构的共享哈希表**。关键性质：命令**串行执行**（单线程内核）→ 单条命令天然原子 |
| **Lua 脚本** | Redis 里的服务端脚本 | 把"多条命令"打包成**一段不可中断执行的临界区**，不需要锁就能获得原子性（类似"把 CAS 循环搬到服务端一次做完"） |
| **nginx** | Web 服务器 + 反向代理 | 静态文件服务 + 前置路由（`/api/*` 转发到后端 8081），可扩展成负载均衡 |
| **RabbitMQ** | 消息队列 | 生产者-消费者队列：交换机（按路由键做路由表）→ 队列 → 消费者；支持 ack 确认、TTL 超时、死信队列 |
| **Redisson** | 分布式锁库 | **跨进程的互斥量（mutex）**，锁变量放在 Redis，附带可重入、自动续期（看门狗）、多节点连锁 |
| **ThreadLocal** | 语言级设施 | 线程局部存储：每个线程一份独立副本，用来在同一次请求的调用链里隐式传递用户身份 |
| **拦截器** | 框架机制 | HTTP 请求处理管线上的中间件（类似 filter chain / AOP 切面） |
| **JUnit + MockMvc** | 测试框架 | 单元测试 + 不启动真实容器的 HTTP 层测试 |

**Redis 的数据结构**（README 反复用到，先记住这张表）：

| 结构 | 语义 | 典型用途 |
|---|---|---|
| String / Hash | 字符串 / 字段表 | 缓存对象、会话信息 |
| Set | 无序集合 | 关注关系、去重 |
| **ZSet** | **带 score 的有序集合，底层跳表** | 排行榜、按时间排序、地理索引 |
| **BitMap** | 位数组（本质是 String 的位视图） | 签到、二值统计 |
| **HyperLogLog** | 概率基数估计器 | UV 去重计数（近似） |
| **GEO** | 地理位置（基于 ZSet + geohash 编码） | 附近商铺 |

## 2. 八个模块：问题 → 方案 → 权衡

### 2.1 短信登录：从"有状态服务"到"共享会话表"

**问题**：传统做法把登录态存在每台 Tomcat 进程的内存（HTTP Session）里，服务从 1 台扩到 N 台后，请求落到不同机器就"掉登录"。本质是**有状态服务的会话粘性问题**。

**方案**：把会话表外置到 Redis —— 登录成功生成一个随机 **token 当 key**，用户信息（id/昵称/头像）作为 value 存进去并设 TTL；客户端之后每次带 `authorization: token`。

**两层拦截器**（这是 README 强调的设计点）：

1. **全局拦截器**：对所有路径生效 —— 取 token、查 Redis、把用户放进 ThreadLocal、**顺带续期**（活跃就不过期）。因为"刷新登录态"应该是**所有请求**的副作用。
2. **登录校验拦截器**：只对需要登录的路径生效，ThreadLocal 里没人就返回 401。

> 分两层的理由：职责单一 + 避免对公开接口（店铺列表、热门博客）做无意义的校验；而且第一层已经把用户查好了，第二层直接复用，不用重复查 Redis。

**替代方案**：JWT 把认证信息放在客户端自包含的 token 里（无状态、可签名防篡改），但不能主动失效（需要额外的黑名单表）—— 这是"服务端状态 vs 客户端状态"的经典取舍。

### 2.2 缓存：三大经典失效模式（穿透 / 雪崩 / 击穿）

前提是 **Cache Aside（旁路缓存）** 模式：读时缓存不命中就查库并回填；写时改库 + 删缓存。缓存与数据库的一致性是**最终一致**，不是强一致。

| 模式 | 触发条件 | 后果 | README 给的解法 |
|---|---|---|---|
| **穿透** | 查**不存在**的数据（如伪造负数 id），缓存永远不命中 | 每次请求都打到 DB | ① 参数校验（类型/范围）② **布隆过滤器**（空间高效地判"一定不存在/可能存在"）③ **缓存空值 + 短 TTL**（本项目采用） |
| **雪崩** | 大量 key **同时过期**，或缓存整体不可用 | 请求洪峰同时砸向 DB | ① 互斥回源（串行化）② 过期时间加**随机抖动**打散 ③ **缓存预热** |
| **击穿** | **单个热点 key** 过期，瞬时高并发同时重建 | 该热点瞬间把 DB 打穿 | ① **互斥锁重建**（时间换空间，串行）② **逻辑过期 + 异步重建**（空间换时间，可能读到旧数据） |

**击穿两种解法对比**（README 的核心权衡之一）：

| | 互斥锁 | 逻辑过期 |
|---|---|---|
| 思路 | 只有一个线程能去查库重建，其余等待 | 值里带"逻辑过期时间"，命中即返回旧值，另起线程重建 |
| 一致性 | 高（不会有脏读） | 低（可能短暂读到旧数据） |
| 性能 | 差（并发退化为串行） | 好（请求永不阻塞在重建上） |
| 代价 | 需处理死锁、锁续期 | 需要预热 + 额外内存 |

**关于重建线程**：把重建放到后台线程的意义是——① 用户请求不阻塞；② 重建任务收敛到一个线程，避免"缓存失效瞬间 N 个并发同时查库"；③ 即使重建失败，系统还能靠旧数据提供服务（降级）。

**强一致场景**：README 另提了用 Redisson 的**读写锁**（读者共享、写者独占，读写互斥）保护读改写路径。

### 2.3 秒杀：四个问题一路打怪升级（本项目最核心的一节）

**① 超卖 —— 并发下的 check-then-act 竞态**

> 线程 A 读到库存 1 → 还没扣减 → 线程 B 也读到 1 → 两人都扣减 → 卖出 2 张。

两种解法（README 用标准的锁理论对比）：

- **悲观锁**：读之前就加锁，让临界区串行化。简单，但并发退化、有死锁风险。
- **乐观锁（本项目）**：不加锁，**提交时用条件更新验证** —— CAS 思想的 SQL 版：
  ```sql
  UPDATE tb_seckill_voucher SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0
  ```
  只要影响行数为 0 就说明竞态失败。README 特别点出：库存这种场景不需要"读到的值和写回时一致"（版本号方案），**直接用 `stock > 0` 当条件**更宽松、成功率更高。

**② 一人一单 —— 单机锁不够了**

`WHERE user_id = ? AND voucher_id = ?` 先查再插，是又一个竞态。在**多进程集群**里，JVM 内部的 `synchronized` 只能锁住本进程 → 必须用**分布式锁**（互斥变量放在所有进程都能访问的 Redis 里）。

README 用 Redisson 讲透了分布式锁的四个工程难题：

- **可重入**：同一线程可重复获取同一锁（用 Hash 存：大 key = 锁名，小 key = 持有者标识，value = 重入次数），否则自己等自己死锁
- **可重试**：拿不到不直接失败，自旋等待，锁释放后立刻拿到 → 高并发下吞吐更好
- **看门狗（Watch Dog）**：业务没跑完而锁 TTL 到了会出大问题（锁提前释放 → 互斥失效），所以后台定期续期
- **主从一致性**：主从复制是异步的，主节点宕机可能导致锁丢失；Redisson 的**连锁（multiLock）**做法是在 N 个独立节点上都要拿到锁才算成功，用可用性换安全

**③ Lua 脚本 —— 用原子性换掉锁**

最终形态把"判库存 + 判是否重复下单 + 扣库存 + 记录下单用户 + 发消息"写成一个 **Lua 脚本**在 Redis 里执行：

- Redis 单线程 + 脚本整体执行 ⇒ 这一整段是**原子的**，天然互斥，**不需要加锁**
- 返回值语义化：`0` 成功 / `1` 库存不足 / `2` 重复下单
- 顺带减少网络往返（多条命令 → 一次调用）

**④ 异步下单 —— 把耗时路径搬出关键路径**

压测发现瓶颈：整个下单链路是**串行走数据库**的四步（查券、查订单、减库存、创建订单），还要加锁，吞吐很低。

改造后的架构（**把"资格校验"和"真正落库"分离**）：

```
请求 → Redis Lua 预检（快，原子）→ 通过就发消息（快）→ 立即返回订单号
                                   ↓
                       消息队列 → 后台消费者：落库 + 扣 MySQL 库存（慢，但用户不等）
```

- 前端拿到的"下单成功"是** Redis 侧的资格预检通过**，真正的订单记录稍后才落库（异步最终一致）
- 用户侧延迟从"四次 DB 写"降到"一次 Redis 脚本 + 一次发消息"

**消息中间件的演进**（README 里两代都讲了）：

- **第一代：Redis Stream + 消费者组**。特点：消息分流（组内消费者各取一部分）、**消费位点**（宕机重启能从上次位置续读）、**ACK + pending-list**（未确认消息会被记录，可回溯重放）。语义上是"至少消费一次"。
- **第二代（当前实现）：RabbitMQ**。更专业的消息中间件：

  | 机制 | 作用 |
  |---|---|
  | 交换机 + 路由键（Direct） | 按 key 精确路由到队列（等价于"路由表 + 队列"） |
  | 手动 ACK | 消费成功才确认，避免消息丢失 |
  | `basicNack(requeue=false)` | 失败消息直接丢弃，**防止"毒消息"被无限重投阻塞队列** |
  | TTL + 死信队列（DLX） | 队列里超过 10 秒没被消费的消息 → 转到死信交换机 → 死信队列，由另一个消费者兜底（**延迟重试**的标准实现手法） |
  | 幂等去重 | 消费者先按订单 ID 查库，已存在就跳过 —— "至少一次投递 + 消费端幂等" ≈ 效果上的恰好一次 |

  落库与扣减库存放在**同一个事务**里，保证不会只写单不扣库存。

### 2.4 点赞排行榜：ZSet（跳表）

**为什么不用 MySQL**：点赞是高频写、且要按时间排序取前几名；关系库的写入和排序成本都高。

**方案**：`ZADD blog:liked:<blogId> <时间戳> <userId>`，score 用时间戳 → 天然按点赞时间排序；`ZSCORE` 判断"我点过没"；DB 里只维护一个计数。

> ZSet 底层是**跳表（skiplist）**：期望 O(log n) 插入 / 查询 / 取排名区间，这就是"按 score 有序 + 支持范围查询"的数据结构基础。

### 2.5 共同关注：Set 交集

关注关系双写（MySQL 存明细、Redis Set 存 id 集合），求共同关注就是两个 Set 的 `SINTER`（集合交集）。本质是把关系代数里的 ∩ 交给服务端现成的结构去做。

### 2.6 附近商铺：GEO

**核心思想**：把二维的"经纬度邻近查询"降成一维有序结构的范围扫描 —— 用 **geohash** 把经纬度编码成一个可比较的整数（编码前缀相同 = 空间邻近），塞进 ZSet，于是"半径 5km 内的店铺"≈"在一维区间上取一段"。距离用 **Haversine 公式**算球面距离（误差 < 0.5%）。

命令层面：`GEOADD`（写）/ `GEOPOS`（取坐标）/ `GEODIST`（两点距离）/ `GEOSEARCH`、旧版 `GEORADIUS`（半径搜索，可带 `WITHDIST` 返回距离、`ASC` 按距离排序、`COUNT` 限量）。

**分页的小技巧**（README 唯一一个偏 tricky 的点）：GEO 查询没有 offset，所以先取"前 end 个"，再在应用层 `skip(from)`，这样既保持按距离有序、又实现了分页。

### 2.7 用户签到：BitMap

**表示**：`SETBIT sign:<userId>:<yyyyMM> <今天-1> 1` —— 一个月的签到状态就是 31 个 bit（4 字节）。

**连续签到怎么算**（位运算练习）：

1. `BITFIELD key GET u<今天> 0` 一次性取出本月 1 号到今天的所有位，作为一个十进制整数
2. 从最低位开始：`num & 1` 判断当天是否签到；是则计数并 `num >>>= 1` 右移一位继续；遇到 0 就停止

### 2.8 UV 统计：HyperLogLog

**问题**：统计"独立访客数"（同一用户多次访问只算 1 个）。精确做法是用 Set 记住每个 user_id，内存 O(去重数)，上百万用户就很贵。

**方案**：HyperLogLog 是**概率基数估计**结构 —— 不存元素本身，只存哈希值的统计特征（观测"前导零长度"的最大值来外推基数）。空间 O(log log n)，**单个结构 ≤ 16KB、误差 < 0.81%**。命令：`PFADD` / `PFCOUNT`。

> 同一家族的思想：布隆过滤器（判存在，允许假阳性）、HLL（估基数，允许误差）—— 都是"用一点点正确性换巨大的空间节省"。

## 3. 贯穿全篇的五个设计思想

1. **把状态外置**：会话、库存、点赞、关注、位置都搬到共享的 Redis，服务进程变得无状态 → 可水平扩展（对应 2.1 的集群问题）
2. **让检查与修改原子化**：Lua 脚本、条件 UPDATE（CAS）、单线程串行 —— 都是"消除 check-then-act 窗口"的不同手段
3. **把耗时操作移出关键路径**：异步下单、后台线程重建缓存（延迟/吞吐的取舍）
4. **选对数据结构就是优化**：ZSet 管排序、BitMap 管二值、GEO 管邻近、HLL 管去重计数 —— 数据结构选对了，算法复杂度就下来了
5. **至少一次投递 + 幂等 = 可靠**：分布式下"恰好一次"很难，工程上用 ACK/重试 + 去重键来逼近

## 5. ⚠️ README 描述 vs 当前代码（我逐文件核对过）

README 记录了项目的**演进过程**，所以它描述的方案可能不是代码现在跑的方案。看代码时注意这几处：

| README 写的 | 代码里实际的 |
|---|---|
| "基于 stream 结构作为消息队列" | 已换成 **RabbitMQ**（`QueueConfig` + `SeckillVoucherListener`）；README 自己也标注了"✅改进：使用 RabbitMQ 更适合" |
| "使用 Redis 分布式锁解决一人一单" | 秒杀路径现在靠 **Lua 脚本的原子性**完成（`seckill.lua` 里 `SISMEMBER` + `SADD`）；`SimpleRedisLock` / `RedissonConfig` 仍留在仓库但没有被秒杀流程使用 —— 分布式锁那条线是"方案演进史" |
| 缓存章节讲 Cache Aside / Redisson 读写锁 | 店铺缓存实际走 **逻辑过期**（`CacheClient.queryWithLogicalExpire`）；`queryWithPassThrough`（空值缓存那条路）**没有任何调用点** |
| 库存扣减"用乐观锁" | 两处都有：Lua 里预扣 Redis 库存，消费者落库时再用 `stock > 0` 条件更新 MySQL（双保险） |
| `ThreadLocalUtls.getUser()` | 实际类名是 `UserHolder`（`com.hmdp.utils`） |
| 未提及 | 应用启动时 `@PostConstruct` 会用 `SETNX` 把 `tb_seckill_voucher` 的库存预热进 Redis（`seckill:stock:<id>`），**只在 key 不存在时写** |

另外两个已知的行为特点（README 没写，但压测/使用时会遇到）：

- 秒杀接口每次请求都会 `checkTimeWindow()` 查一次 MySQL（券信息没缓存），高并发下这是一个明显的 DB 压力点
- 点赞接口 `updateLike` 是 check-then-act（先查 ZSet 再 `liked+1`），并发下同一用户可能把计数加多次

> 想知道怎么把这些拿去做并发验证（造数据、发压、判读超卖/一人一单），见同目录的 `docs/concurrency-testing.md`。
