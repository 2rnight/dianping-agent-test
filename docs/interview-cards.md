## 0. 开场：项目介绍

**一句话版**：一个前后端分离的"大众点评"简化实现，重点解决**高并发下的缓存一致性与秒杀下单**问题。

**1 分钟版**（挑你要强调的点）：

> 后端 Spring Boot + MyBatis-Plus，MySQL 存业务数据，Redis 做缓存/库存/排行榜/地理位置/签到，RabbitMQ 做异步下单，nginx 托管前端并反代 `/api`。
> 业务上有 8 块：短信登录、商户缓存、优惠券秒杀、达人探店（点赞关注）、附近商铺、签到、UV 统计。
> 技术亮点集中在三处：**用 Redis 统一管理会话和热点数据**、**用 Lua 脚本把秒杀资格校验做成原子操作**、**用消息队列把下单落库从请求链路里剥离**。

**想秀数据就补一句**：

> 我用 200 并发抢 100 张券压过：成功正好 100、库存扣到 0、订单落库 100 条、无一人多单，和 Redis/MySQL 两侧数据完全对得上。

## 1. 会话与登录：Redis 替代 Session

**30 秒版**
1. 问题：Tomcat 集群下 Session 存在各自进程内存里，请求飘到别的机器就"掉登录"——根因是有状态服务没法水平扩展。
2. 方案：把会话外置到 Redis，登录成功生成随机 `token` 作 key，用户信息存 Hash，请求头带 `authorization` 由拦截器还原用户。
3. 效果：服务变成无状态可任意扩容；顺带用 TTL 实现"活跃续期"，不活跃自动登出。

**追问链**

| 问 | 答 |
|---|---|
| 为什么不用 JWT？ | JWT 客户端自包含、无需查 Redis，但**不能主动失效**（要登出得配黑名单，等于又把状态搬回服务端）；这里需要"改密码即踢下线""活跃续期"，用 Redis 反而简单。 |
| 你的登录流程？ | 发验证码存 Redis（2 分钟）；登录校验验证码 → 查/建用户 → 生成 UUID token → `HSET login:token:<token> id/nickName/icon` + 30 分钟 TTL → 返回 token。 |
| 为什么要两层拦截器？ | 第一层对所有路径生效（取 token、查 Redis、放 ThreadLocal、续期），第二层只拦需要登录的路径做校验；拆开是为了**避免公开接口被无谓校验**，而且第二层直接复用第一层查到的用户，不重复查 Redis。 |
| ThreadLocal 会不会有内存泄漏/串号？ | 会——线程池复用线程，所以必须在 `afterCompletion` 里 `removeUser()`；代码里确实做了（注释也写了防串号）。 |
| 为什么不用 `getSession()`？ | 已经不用 HttpSession 了，登录态完全由 Redis + token 承担；`HttpSession` 参数是历史遗留。 |
| 多端登录互踢怎么做？ | 会话表里按 userId 记一份当前 token（或存 token 列表），登录时删旧 key 即可，这是 Redis 会话相比 JWT 的直接优势。 |

## 2. 缓存一致性：Cache Aside

**30 秒版**
1. 读路径：先查缓存，命中返回；未命中查库再回填，并设 TTL。
2. 写路径：**先改数据库，再删缓存**，而不是更新缓存——避免并发写的乱序覆盖。
3. 一致性是最终一致，用 TTL 兜底；要更强一致性就把缓存更新放进事务/用读写锁。

**追问链**

| 问 | 答 |
|---|---|
| 为什么删缓存而不是更新缓存？ | 更新缓存并发下可能乱序覆盖（后写的先到），而且如果写多读少，更新缓存是白算；删除是幂等的、懒加载的。 |
| 先删缓存再改库行不行？ | 有"删完缓存、库还没改完，读请求把旧值又读回缓存"的窗口，所以是**先改库再删缓存**（配合延迟双删更稳）。 |
| 删除失败怎么办？ | 兜底是 TTL；更严格可以用**消息队列投递删除事件重试**，或订阅 MySQL binlog（Canal）。 |
| 为什么不强一致？ | 缓存和 DB 是两个存储，强一致要加分布式事务/锁，代价大于收益；这个业务能容忍秒级不一致。 |
| 项目里哪里用了？ | 店铺详情走逻辑过期（见下卡）；商品/店铺更新走"改库 + 删缓存"（`ShopServiceImpl#update`）。 |

## 3. 缓存穿透 / 雪崩 / 击穿

**30 秒版**
1. **穿透**：查不存在的数据，缓存永远不命中——用参数校验、布隆过滤器，或**缓存空值 + 短 TTL**（本项目）。
2. **雪崩**：大量 key 同时过期或缓存不可用——给 TTL 加随机抖动、互斥回源、缓存预热。
3. **击穿**：单个热点 key 失效瞬间被并发重建——用互斥锁重建（时间换空间）或逻辑过期 + 异步重建（空间换时间，可能脏读，本项目店铺缓存用的就是它）。

**追问链**

| 问 | 答 |
|---|---|
| 逻辑过期具体怎么实现？ | 缓存值不是裸对象，而是 `{data, expireTime}`；命中后判断 `expireTime`，**未过期直接返回，已过期也返回旧值**，同时抢 `SETNX` 锁、成功者提交异步任务重建缓存。 |
| 为什么要两个"过期"？ | Redis 的 TTL 负责物理回收/兜底，`expireTime` 是业务上的"软过期"，二者解耦才能做到"永远有数据可返回"。 |
| 异步重建的锁没释放会怎样？ | 会一直重建不了（只有拿到锁才重建）；所以代码在 `finally` 里释放，且锁有 10 秒 TTL 兜底。注意锁的 key 和缓存 key 不是同一个（代码注释专门强调过这个坑）。 |
| 逻辑过期有什么代价？ | ① 必须**提前预热**，没预热过的 key 直接返回 null（不是回源）② 可能读到旧数据 ③ 多占内存。 |
| 互斥锁和逻辑过期怎么选？ | 一致性优先（如库存、订单状态）→ 互斥锁；可用性优先（商品详情、排行榜）→ 逻辑过期。 |
| 布隆过滤器有什么局限？ | 只能判"**一定不存在**"，说"存在"时有假阳性；而且标准布隆**不支持删除**（要 Counting Bloom / Cuckoo）。 |
| 空值缓存要注意什么？ | 一定要设**短 TTL**，否则数据后来真的存在了，缓存里还是空值 → 业务性错误。 |

## 4. 秒杀（一）：超卖与乐观锁

**30 秒版**
1. 超卖是典型的 check-then-act 竞态：多个线程都读到库存 1，然后都扣减。
2. 悲观锁是提前加锁让临界区串行；本项目用**乐观锁的条件更新**：`UPDATE ... SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0`，影响行数为 0 就说明被抢先。
3. 库存场景不需要版本号，直接拿 `stock > 0` 当条件——比"读到的值和写回时一致"宽松，成功率更高。

**追问链**

| 问 | 答 |
|---|---|
| 什么是 CAS？ | Compare-And-Swap：V=目标变量、E=预期值、N=新值，仅当 V==E 时原子地写成 N；对应到 SQL 就是 `WHERE 条件` + `UPDATE`，靠数据库的行锁和影响行数保证。 |
| 乐观锁和悲观锁怎么选？ | 冲突少、读多写少 → 乐观锁（失败重试成本低）；冲突激烈、写多 → 悲观锁（避免反复失败重试）。 |
| 乐观锁失败率高怎么办？ | ① 放宽条件（本项目用 `stock > 0`）② 分段/分桶（把库存拆成 10 份并行抢）③ 改异步（最终方案就是把它移出请求链路）。 |
| 那你还加锁吗？ | 秒杀路径最终**不用锁**——判库存、扣库存、记下单用户都在一个 Lua 脚本里原子完成。 |

## 5. 秒杀（二）：一人一单与分布式锁

**30 秒版**
1. 一人一单如果用"查订单 → 不存在则插入"，也是竞态；单机 `synchronized` 在集群下只锁住本进程，所以需要**分布式锁**。
2. 分布式锁要解决四件事：**可重入**（Hash 存持有者 + 重入次数）、**可重试**（自旋等待而不是直接失败）、**看门狗续期**（业务没跑完不能提前释放）、**主从一致性**（主从异步复制可能丢锁，用 Redisson 连锁在多数节点上都加锁）。
3. 但最终线上路径用的是 **Lua 脚本的原子性**：`SISMEMBER` 判断是否下过单 + `SADD` 记录，天然互斥，连锁都省了——**能用原子操作解决的，就别用锁**。

**追问链**

| 问 | 答 |
|---|---|
| 为什么要可重入？ | 业务里可能有嵌套加锁的调用；不可重入会自己等自己 → 死锁。 |
| 看门狗怎么工作的？ | 加锁成功起一个后台定时任务，每隔锁 TTL 的 1/3 检查业务是否还持有锁，是就续期；业务结束手动释放。 |
| 锁超时了业务还没做完怎么办？ | 这正是看门狗要解决的；此外要评估临界区耗时、给足 TTL，并保证释放时校验持有者（防误删别人的锁）。 |
| Redisson 连锁（multiLock）解决什么问题？ | 主从切换会丢锁：主节点写入后未同步就宕机，从节点升主后没人知道锁存在。连锁要求 N 个**独立**节点都加锁成功，锁才不会因单点故障失效；代价是可用性下降、延迟上升。 |
| 你用哪种锁？ | 代码里保留了 `SimpleRedisLock`（SETNX 版）和 Redisson 配置，但**秒杀路径已改为 Lua**，分布式锁这条线属于方案演进；如果问"为什么不用了"，答：Lua 一次原子执行就完成了判断和修改，不需要额外的锁开销。 |

## 6. 秒杀（三）：Lua 原子预检

**30 秒版**
1. 需求：一次操作里要完成"判库存、判是否重复下单、扣库存、记录用户、产生订单号"五件事，任何中间态被别的请求插进来都会出错。
2. 方案：把这五步写成一个 **Lua 脚本**交给 Redis 执行——Redis 命令是单线程串行的，脚本会被整体执行，天然原子，不用加锁。
3. 效果：一次网络往返、无锁、无竞态；脚本用返回值表达业务语义：`0` 有资格、`1` 库存不足、`2` 重复下单。

**追问链**

| 问 | 答 |
|---|---|
| 为什么 Redis 单线程就不用担心原子性？ | 单线程意味着命令一个接一个执行，任何命令/脚本执行期间不会被其它命令打断；所以"多条命令组合"只要包进脚本就是原子的。 |
| Lua 脚本里做了什么？ | 读 `seckill:stock:<id>` 判库存 → `SISMEMBER seckill:order:<id> <userId>` 判重 → `INCRBY -1` 扣减 → `SADD` 记录 → 返回码（脚本里还留了一个 `XADD stream.orders`，见第 16 卡）。 |
| Lua 有什么限制？ | 脚本执行会**阻塞整个 Redis**，所以必须短小（别放循环、别访问外部系统）；不要在脚本里用随机数/时间（主从/集群下不一致）。 |
| 库存为什么放 Redis 而不是直接扣 MySQL？ | 每秒几千请求打 MySQL 行锁撑不住；Redis 内存操作 + 原子脚本是数量级的差别。 |
| 用户身份哪来的？ | 拦截器放在 ThreadLocal 里，脚本的 ARGV 带上 `userId`。 |
| 脚本执行失败（比如库存 key 不存在）怎么办？ | 返回 -1 → 上层转成"秒杀失败"；库存 key 由应用启动时的预热逻辑（`@PostConstruct`，`SETNX` 只在不存在时写）或建券接口写入。 |

## 7. 秒杀（四）：异步下单与消息队列

**30 秒版**
1. 压测发现瓶颈：查券、查订单、减库存、建订单四步**串行打 MySQL**，还加锁，吞吐上不去、平均耗时高。
2. 方案：把"资格校验"和"真正落库"分离——Redis 脚本校验通过后**只发一条消息就立刻返回订单号**，MQ 消费者在后台慢慢落库、扣 MySQL 库存。
3. 代价是"下单成功"变成最终一致（用户拿到的订单号稍后才在库里出现），换来的是请求链路从"4 次 DB 操作"降到"1 次 Redis 脚本 + 1 次发消息"。

**追问链**

| 问 | 答 |
|---|---|
| 消息丢了怎么办？ | 生产者侧异常会抛出并记录（`convertAndSend` 包在 try-catch 里），消费侧用**手动 ACK**：处理成功 `basicAck`；异常 `basicNack(requeue=false)` 丢弃，避免毒消息无限重投阻塞队列。 |
| 为什么队列还配了 TTL 和死信队列？ | QA 队列设 10 秒 TTL，消息超时未消费就变成死信经交换机 Y 转到 QD；QD 有消费者兜底处理——这是"延迟重试/补偿"的标准搭法，也能兜住消费者长时间不可用的场景。 |
| 重复消费怎么办？ | 消费端**幂等**：先按订单 ID `getById` 查库，存在就跳过；且落库与扣库存放在**同一事务**里，避免只写单不扣库存。 |
| 为什么说"至少一次 + 幂等 = 恰好一次"？ | 分布式下"恰好一次投递"无法保证，工程做法是允许重复投递，用去重键把重复消费的副作用消掉。 |
| 为什么从 Redis Stream 换成 RabbitMQ？ | Stream 够用（消费者组、位点、ACK、pending-list）但功能弱；RabbitMQ 有成熟的交换机/路由、死信、TTL、手动 ACK、管理后台，更适合生产。 |
| 死信队列会不会消息爆炸？ | 会——所以 `requeue=false` 丢弃 + 日志告警；真要重试应该用延迟队列分级重试 + 最大重试次数。 |
| 为什么不用 Kafka？ | 单体应用的秒杀削峰，RabbitMQ 的路由和死信更贴合；Kafka 强在吞吐与流式生态，这个量级用不上。 |

## 8. 全局唯一 ID

**30 秒版**
1. 订单号不能用自增主键（分库分表会撞、还会暴露业务量），也不能用 UUID（无序、占空间、索引不友好）。
2. 方案：**时间戳 + 序列号**拼一个 64 位 long——高位是"当前秒 − 自定义起始时间（2022-01-01）"，低 32 位是 Redis `INCR` 出的当日自增序列，`timestamp << 32 | count`。
3. 效果：全局唯一、趋势递增（对索引友好）、每秒每 key 可产 2^32 个，且不依赖数据库。

**追问链**

| 问 | 答 |
|---|---|
| 为什么序列号用 Redis 而不是数据库自增？ | Redis `INCR` 是内存原子操作，性能高；key 里带日期（`icr:order:yyyy:MM:dd`）→ 每天从 1 开始，方便统计"今天下了多少单"。 |
| 为什么自定义起始时间？ | 压缩时间戳占用的位数（不用从 1970 算），把更多位留给序列号，延长可用年限。 |
| 时钟回拨怎么办？ | 这套方案只依赖"秒级时间戳"，回拨会导致重复风险；严格实现（雪花算法）需要检测回拨并等待/报警。 |
| 64 位里 32 位序列号够吗？ | 单 key 每秒 42 亿，远超需求；不够还可以用"时间戳 + Redis 自增整段"的混合方案。 |
| 怎么验证不重复？ | 并发压 `nextId` 收集结果去重计数（仓库里 `testIdWorker` 是 300 线程 × 100 次，但只打印没断言——改进点是收进 Set 断言 size）。 |

## 9. 点赞排行榜：ZSet

**30 秒版**
1. 需求：一人一赞、要能按点赞时间排序取前几名，读多写多，放 MySQL 两头不讨好。
2. 方案：用 ZSet 存 `blog:liked:<blogId>`，member 是 userId、**score 是点赞时间戳**——天然按时间有序，`ZSCORE` 判重、`ZRANGE` 直接拿榜单，MySQL 里只维护一个计数字段。
3. ZSet 底层是**跳表**，插入/查询/区间扫描都是 O(log n)。

**追问链**

| 问 | 答 |
|---|---|
| 为什么 score 用时间戳？ | 让"点赞顺序"和"排序"用同一个字段表达，取前 5 名就是 `ZRANGE key 0 4`。 |
| 取消点赞怎么做？ | `ZREM` + 数据库计数 −1。 |
| 跳表和红黑树/B+ 树比？ | 跳表实现简单、范围查询友好、并发实现容易（Redis 单线程所以这点不重要），期望 O(log n)；B+ 树为磁盘页设计，内存结构用不上。 |
| 这个实现有什么问题？ | 是 check-then-act："先 `ZSCORE` 判没点过 → 再 `liked+1` → 再 `ZADD`"，**并发下同一用户可能把计数加多次**（ZADD 幂等所以集合仍只有 1 条）。修法：Redisson 锁，或把"判断 + 计数"做成原子操作。 |
| 更高并发怎么办？ | 点赞写 Redis、计数用 `INCR` 累积后定时刷库（或异步解耦），别让每次都写 MySQL。 |

## 10. 关注 / 共同关注：Set

**30 秒版**
1. 关注关系落 MySQL（明细、可追溯），同时把关注对象的 id 写进 Redis Set `follows:<userId>`。
2. 共同关注 = 两个 Set 求交集 `SINTER`，直接把关系代数的 ∩ 交给 Redis。
3. 取关同步删两份数据，保证两侧一致。

**追问链**

| 问 | 答 |
|---|---|
| 为什么还要存 MySQL？ | Redis 可能丢数据（宕机/淘汰），MySQL 是事实来源，Redis 是可重建的读模型。 |
| 大 V 有几千万粉丝，Set 会不会太大？ | 会——大 V 可以用分片/位图/近似结构，或只在需要时按需查库；普通用户用 Set 完全没问题。 |
| 关注流（Feed）怎么推？ | 推模式：发博客时写粉丝的收件箱（`feed:<userId>`，用 ZSet 按时间排序）；本项目用的是**拉模式**：读的时候查我关注的人的最新博客。推拉结合是大 V 场景的常见答案。 |
| 交集之外还常用什么？ | 差集（`SDIFF`）做"可能认识的人"，并集（`SUNION`）做合并关注列表。 |

## 11. 附近商铺：GEO

**30 秒版**
1. 需求：按距离查附近店铺并按距离排序、分页，二维邻近查询在关系库里要算全表距离，很贵。
2. 方案：Redis GEO —— 用 **geohash** 把经纬度编码成一维可比较的整数塞进 ZSet，"半径内查询"就变成一维区间检索；距离用 **Haversine 公式**算球面距离（误差 <0.5%）。
3. 实现：`GEOSEARCH key FROM lon lat BYRADIUS 5000 m WITHDIST ASC COUNT n`，前端传坐标，后端取前 `end = 页号 × 每页` 条再在应用层 `skip(from)` 完成分页。

**追问链**

| 问 | 答 |
|---|---|
| geohash 为什么能降维？ | 它把空间递归四分并交替编码经纬度，**编码前缀相同 ⇒ 空间邻近**；一维上相邻的块在二维上也大概率相近（边界格子需要额外检查邻居，Redis 内部处理了这一层）。 |
| GEO 底层是什么？ | 就是 ZSet（score 是 geohash 整数），所以能用 ZSet 的命令做范围扫描。 |
| 为什么取前 end 条再 skip？ | Redis GEO 查询没有 offset，只能先取"前 end 条"再在应用层丢掉前 `from` 条，这样仍保持按距离有序。 |
| 分页有什么隐患？ | 数据变动会导致跨页重复/漏项（没有稳定游标）；更稳的是游标分页（记住上次的距离/score）。 |
| 没有坐标参数会怎样？ | 走数据库分页 `WHERE type_id = ?`（代码里就是 `x == null || y == null` 的分支）。 |
| 5 公里限制有什么影响？ | 超出半径的店**根本不返回**（不是排序靠后）；前端把坐标写死在杭州，所以数据必须落在半径内才看得到。 |

## 12. 用户签到：BitMap

**30 秒版**
1. 签到是"某天有没有"的二值状态，用位图存：一个月 31 天只占 4 字节，key 设计成 `sign:<userId>:<yyyyMM>`。
2. 签到：`SETBIT key (今天-1) 1`；同一位置写 1 是幂等的，并发重复签到天然安全。
3. 连续天数：`BITFIELD key GET u<今天> 0` 一次取出本月 1 号到今天的位串（一个十进制整数），再从最低位开始数连续的 1。

**追问链**

| 问 | 答 |
|---|---|
| 为什么用 BitMap 而不是一行记录？ | 空间差两个数量级（bit vs 整行），且统计"本月签到几天"用 `BITCOUNT` 一条命令搞定。 |
| 连续签到怎么数？ | 取出的整数从最低位（今天）开始 `num & 1` 判断、`num >>>= 1` 右移，遇到 0 停止；位数对应当月第几天，所以天然是"从今天往前连续"。 |
| 跨月怎么办？ | key 按月切分（`yyyyMM`），跨月连续需要读上个月的 key 继续数。 |
| 缺点？ | 用户 id 稀疏时 offset 会浪费空间（`SETBIT` 会补齐中间所有位）；签到是"每用户每月固定几十位"，所以无所谓。 |
| 位运算还有别的用法吗？ | 用户在线状态、活跃标签、布隆过滤器底层都是位数组。 |

## 13. UV 统计：HyperLogLog

**30 秒版**
1. 需求：统计独立访客数（同一用户多次访问只算一次），精确做法要用 Set 记住所有 user_id，内存随去重数线性增长。
2. 方案：HyperLogLog 是**概率基数估计**结构——不存元素，只存哈希值的统计特征（观测前导零长度最大值来外推基数），空间 O(log log n)。
3. 效果：单个结构 ≤16KB、标准误差 <0.81%，`PFADD` 写入、`PFCOUNT` 读估算值；项目里用 100 万条 `user_id` 做过误差验证（跑一次几秒钟）。

**追问链**

| 问 | 答 |
|---|---|
| 为什么能省这么多空间？ | 均匀哈希后，"观测到的最长前导零"和"集合基数"有统计关系；用分桶（16384 个）+ 调和平均把方差压下来，就不需要存元素了。 |
| 为什么有误差？ | 它是估计不是计数；误差可量化（标准误差 ≈ 1.04/√桶数 ≈ 0.81%）。 |
| 能用它判断某个用户在不在吗？ | 不能——HLL 只回答"有多少"，判存在要用布隆过滤器。 |
| 能合并吗？ | 能，`PFMERGE` 可合并多个 HLL（求并集基数），这是它相对 Set 的另一个优势。 |
| 什么时候不能用？ | 需要精确值（对账、计费）或需要列出具体元素时，必须用 Set/数据库。 |

## 14. 架构与部署（被问"怎么跑起来的"）

**30 秒版**
1. nginx 监听 8080：托管 `html/hmdp` 静态页面，并把 `/api/*` 反代到后端的 8081（前端 axios 的 baseURL 就是 `/api`）。
2. 中间件用 docker-compose 一键起：MySQL（业务数据）、Redis（缓存/库存/队列/地理位置）、RabbitMQ（异步下单 + 管理台 15672）。
3. 应用端口 8081；SQL 初始化脚本在 `src/main/resources/db/hmdp.sql`（含测试数据），Redis 的部分数据（店铺 GEO、秒杀库存预热）需要额外导入。

**追问链**

| 问 | 答 |
|---|---|
| 为什么用 nginx 反代？ | 同源部署避免跨域、静态资源由 nginx 直接托管（后端 MySQL/Redis 不动）、后续可加多实例做负载均衡。 |
| 怎么扩成集群？ | 后端无状态（会话在 Redis）→ 多起几个实例给 nginx upstream 即可；Redis 做主从 + 哨兵/集群；MySQL 主从读写分离；RabbitMQ 做镜像队列。 |
| 压测怎么做的？ | 200 个不同用户（脚本直接造 Redis 登录态）用栅栏同步发压秒杀接口，统计成功/库存不足/重复下单分类，并用 Redis `SCARD`、MySQL 订单数与库存做交叉校验。 |

## 15. 数据卡：把压测结果讲成证据（强烈建议背下来）

**场景**：券库存 100，200 个不同用户同时抢（200 线程同步发车）。

| 观测项 | 结果 | 说明 |
|---|---|---|
| 成功 / 库存不足 | **100 / 100** | 不多不少，正好等于库存 |
| Redis 剩余库存 | 0 | 初始 100 − 成功 100 |
| Redis 已下单用户数（SCARD） | 100 | 一人一单 |
| MySQL 订单数（等 MQ 消费完） | 100 | 异步下单最终一致，没丢消息 |
| MySQL 库存 | 0 | 没有扣成负数 |
| 重复下单查询 | 空 | 无人多单 |

**怎么用**：面试官问"你怎么证明没超卖 / 一人一单真的生效"——这五个数字就是证据，比说"应该没问题"有力得多。

**加分：主动讲性能瓶颈与优化方向**（被问"你的 QPS 多少、瓶颈在哪"时）

> 实测 200 并发吞吐约 70 req/s、P50 2.5 秒，延迟几乎一致说明大家在等同一个资源。按嫌疑排序：① HikariCP 默认连接池只有 10 条；② 秒杀接口每次请求都 `getById` 查一次 MySQL（券信息没缓存）；③ debug 日志同步 IO；④ Windows 上 Docker 转发的网络开销。优化方向是把券信息缓存进 Redis、放大连接池、把日志级别调到 info。

## 16. 危险区：面试官看代码时的诚实答法

> 原则：**不装**。承认"这是演进过程/已知问题 + 说出修法"，比被戳穿强得多，而且这本身就是加分的工程素养。

| 可能被问的点 | 代码实际情况 | 怎么答 |
|---|---|---|
| "你 README 写的 stream 消息队列，代码里怎么是 RabbitMQ？" | `seckill.lua` 里**还留着** `XADD stream.orders`，而 Java 侧已经用 `RabbitTemplate` 发 MQ | 方案从 Stream 演进到了 RabbitMQ；脚本里的 `XADD` 是**遗留代码**，实际没人消费 `stream.orders`，属于要清理的技术债（顺手说"这也是我下一步要改的"） |
| "你说用分布式锁做一人一单，锁在哪？" | 秒杀路径靠 Lua 的 `SISMEMBER + SADD`，`SimpleRedisLock`/`RedissonConfig` 没被调用 | 分布式锁是我实现过的方案（可重入/看门狗/连锁都调通了），但最终用 Lua 的原子性替代了它——**能用原子操作就不用锁**，性能更好、也不用处理锁续期 |
| "空值缓存（缓存穿透）代码在哪？" | `CacheClient.queryWithPassThrough` 没有任何调用点，店铺走的是逻辑过期 | 两套方案都实现了，线上跑的是逻辑过期；pass-through 是练习/备选路径，可以按需切换 |
| "点赞并发安全吗？" | `updateLike` 是 check-then-act，并发下 `liked` 会被多加 | 这是我用并发压测发现的问题（同一用户并发 200 次点赞，DB 计数会被加多次、ZSet 仍是 1 条），修法是 Redisson 锁或把判断+计数做成原子操作 |
| "秒杀接口的 DB 压力？" | `checkTimeWindow()` 每个请求查一次 MySQL | 是明显的优化点：券信息完全不变量，可以缓存进 Redis（这也是压测暴露出来的瓶颈之一） |
| "库存预热为什么用 SETNX？" | 只在 key 不存在时写，避免重启覆盖已扣减的库存 | 好处是安全；副作用是**改了 MySQL 库存后 Redis 不会同步**，需要用脚本/接口显式重置——所以压测脚本里专门做了"重置库存"这一步 |
